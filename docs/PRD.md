# Workflow Agent Chat PRD

## 1. 产品定义

**Workflow Agent Chat** 是面向业务任务的对话工作台。用户选择基础模型或已发布的任务助手，用自然语言完成审核、摘要、问答、生成等工作；创建/配置/发布助手仍由上游平台负责。

核心原则：`已发布能力 = Chat 中的助手`。用户界面只谈「助手 / 对话 / 处理状态 / 需要确认」，不暴露编排图、节点或底层执行术语。

### 三层职责边界

**产品职责**：定义用户任务、能力目录、会话规则、状态语言、权限边界和验收标准。回答“要完成什么、何时算完成、异常后下一步是什么”，不把底层执行细节当成用户任务。

**前端职责**：把任务从开始到完成呈现清楚（工作台、助手选择、输入、状态、确认、结果）。不持有密钥、不直连执行层、不伪造执行状态。

**服务端职责**：认证与租户隔离、助手目录、会话与消息持久化、幂等与并发、对执行层的 BFF、错误归因与状态映射。不承载 UI 状态，不复制编排图到 Chat。

### 产品定位

定位是「任务型对话消费端」：选助手 → 对话完成任务 → 需要时确认 → 拿到可复核结果。价值在于三种确定性：

1. 知道当前使用的是哪个助手（或模型）。
2. 知道任务进行到哪一步、是否需要介入。
3. 能拿到可继续、可追踪的结果。

### 产品关系

```text
上游平台（编排 / 发布 / 监控） = 能力生产端
Workflow Agent Chat           = 能力消费端 + 任务工作台
执行 Runtime                  = 运行基础设施
```

本产品不承接表单/流程编辑器上下文，也不复用平台内部 Copilot 页面。

## 2. 非目标

- 不替代 `ai/app` 的 Schema Platform Copilot。
- 不提供 Schema/Flow 编辑器上下文操作。
- 不在 Chat 项目中编辑或发布 Workflow。
- 不把 LangGraph 图复制到 Chat 项目。
- 不让 Chat 直接访问 AI Runtime 数据库。

## 3. 目标用户与场景

| 用户 | 场景 | 价值 |
|---|---|---|
| 业务用户 | 选择一个 Agent 完成审核、提取、问答、生成等任务 | 用对话替代复杂表单操作 |
| 租户管理员 | 控制租户可用 Agent | 安全复用平台能力 |
| 平台管理员 | 在 AI Platform 创建并发布 Workflow | 一次建设，多端消费 |

## 4. MVP 范围

### P0

- 登录态接入（第一阶段支持 Chat Backend 代理现有 JWT，独立账号体系后置）
- Agent Catalog：仅展示当前租户可见、已发布的 Workflow
- 新建会话、会话列表、消息历史
- 用户选择 Agent 并发送文本消息
- 调用 Runtime Open API，保存 Chat Message 与 Runtime Run 映射
- 展示运行中、成功、失败状态和最终结果
- 轮询适配器；统一设计为可替换 SSE
- waiting 状态展示审批卡片，支持 resume
- 取消运行

### P1

- 自动选择 Agent
- 文件附件
- SSE 实时事件流
- Agent 搜索、收藏、最近使用
- 用量、耗时、错误等基础信息

### P2

- 多 Agent 协作展示
- Agent 组合与临时任务链
- 组织级 Agent 权限策略
- 对话分享和外部嵌入

## 5. 核心流程

```text
打开 Chat
  -> 获取 Agent Catalog
  -> 选择 Agent / 后续自动路由
  -> 创建或复用 Session
  -> POST message
  -> Backend 调 Runtime invoke
  -> 返回 runId
  -> 订阅/轮询运行状态
  -> 保存并展示 assistant message
  -> waiting 时展示 HITL
  -> resume 后继续运行
```

## 6. MVP 验收标准

1. 已发布 Workflow 能在 Agent 列表中出现，草稿不可见。
2. 发送一条消息后，用户能看到运行状态和最终输出；刷新页面不会丢失状态。
3. Runtime 返回 `waiting` 时，用户能提交批准/拒绝/答案并继续执行。
4. Chat 会话数据只保存在本项目 MySQL；Workflow 执行数据仍由 Runtime 管理。
5. 用户不能通过 Chat 读取其他租户的 Agent、Session 或 Run。
6. Runtime 不可用时，界面明确显示失败，不产生幽灵消息。

## 7. 关键产品决策

- 第一版以“用户选择 Agent”为主，自动路由必须建立在 Agent Catalog 完整之后。
- Chat 的 session/message 是产品数据；Workflow execution 是基础设施数据，两者通过 `runtime_execution_id` 关联。
- 对外只暴露 Chat Backend API；前端不持有 Workflow Key。

## 8. 信息架构

MVP 不是营销首页，而是直接进入工作台。助手选择是对话初始化的一部分，不是独立的一级产品：

```text
Workflow Agent Chat
├── 工作台 / Chat
│   ├── 新建会话
│   ├── 最近会话
│   ├── 助手选择器
│   ├── 当前对话
│   └── 处理信息（按需查看）
└── 设置
    ├── 个人设置
    └── 使用记录（P1）
```

## 9. UI/UX 设计原则

- **任务优先**：打开即能开始任务，不放大面积营销 Hero。
- **选择明确**：新对话首屏直接展示助手列表；当前助手始终可见；一个会话固定一个助手，换助手创建新对话。
- **通用模型兜底**：没有合适助手时提供“使用通用对话”，由平台模型 BFF 提供。
- **过程透明但不过载**：默认只展示用户状态，处理信息按需查看，不展示完整思考链。
- **结果可操作**：支持复制、下载、重试、继续对话和查看处理信息。
- **人工介入清晰**：`waiting` 必须明显区别于失败；审批动作直接出现在聊天流中。
- **密度适中**：桌面会话列表 + 主聊天区，处理信息使用抽屉；不使用固定 Inspector 右栏。

## 11. 关键交互状态

| 状态 | UI 表现 | 用户动作 |
|---|---|---|
| idle | 空状态 + Agent 说明 + 示例任务 | 开始输入 |
| running | assistant 占位消息 + 执行时间线 | 停止 |
| waiting | 高优先级审批/补充信息卡 | 批准、拒绝、填写 |
| success | 最终结果 + 过程摘要 | 复制、下载、继续 |
| failed | 失败原因 + 可重试按钮 | 重试或更换 Agent |
| cancelled | 已取消状态 | 重新运行 |

## 12. 视觉方向

- 基调：安静、可信、工作型，不做聊天娱乐化。
- 主色：深青绿色用于执行和主操作；暖橙色作为 Agent/任务强调色；红色只用于错误。
- 背景：浅冷灰；内容区保持白色和清晰分隔线。
- 圆角：4-8px；按钮优先使用图标和明确 tooltip。
- 字体：系统无衬线字体；标题克制，避免巨型 Hero 字号。
- Agent 卡片显示图标、名称、短描述、支持的输入类型、最近更新时间。

## 13. 用户术语基线（P-01 冻结）

普通用户界面统一使用以下术语，后端实现名（Agent / Run / Execution / HITL / Published / Workflow）只在文档与 adapter 层使用，不出现在用户主路径：

| 用户术语 | 对应后端概念 | 禁止在 UI 出现 |
|---|---|---|
| 助手 | Agent / Published Workflow | Workflow、Agent、Published |
| 对话 | Session | — |
| 处理状态 | Run.status | Run、Execution、RUNNING 等枚举 |
| 需要确认 | waiting / HITL | HITL、waiting、WAITING_INPUT |
| 处理信息 | run 节点/耗时 | node、timeline、思考链 |

会话固定一个助手：session 创建后绑定 agent，发送时校验一致，换助手只能新建对话（见 P-02）。
