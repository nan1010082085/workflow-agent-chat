# UI/UX 设计说明

> 本文档为交互唯一依据（TASKS P-04）。术语遵循产品基线：普通用户界面只用「助手 / 对话 / 处理状态 / 需要确认 / 处理信息」，不出现 Workflow、Run、Execution、HITL、Published 等内部术语。

## 1. 设计目标

让用户在最少认知负担下完成一个业务任务，并始终理解：当前助手、当前处理状态、下一步动作、最终结果。用户选择的是「助手」，不是 Workflow；处理过程默认轻量展示，详细信息按需查看。

## 1.1 设计判断

当前产品的主任务不是管理助手，而是完成一件事。首屏必须回答：我能在这里完成什么、哪个助手适合这件事、我现在应该输入什么。不能帮助回答这三个问题的一级导航、固定面板或内部术语不进入 MVP 主路径。

## 1.2 职责契约

| 层 | 负责 | 不负责 |
|---|---|---|
| 产品 | 任务模型、能力模型、状态语言、权限与验收 | UI 装饰、猜测底层接口 |
| 前端 | 任务启动、助手选择、消息流、确认、结果操作、响应式 | 鉴权决策、保存密钥、直接调用 Runtime、猜测失败原因 |
| 服务端 | 身份、租户隔离、目录、会话消息、幂等、Runtime/模型适配、稳定错误 | 具体 UI 布局、暴露底层对象 |

## 2. 信息架构

### 工作台（默认首页）

桌面采用「会话导航 + 聊天主区」双区结构；处理信息为**按需抽屉**，不固定占据右栏：

- 左栏 260-300px：会话导航。负责会话切换和新建对话。
- 主区：任务对话。新对话展示任务引导和助手列表；已有对话展示当前助手、消息流和输入框。
- 处理信息抽屉（按需，右侧滑出 320-360px）：当前对话的处理状态、耗时与节点摘要；默认收起。

> 不再固定渲染 Inspector 右栏。处理信息只在用户点击「处理信息」或出现「需要确认」时按需打开。

### 助手列表

助手列表服务于新对话初始化，不承担独立导航。每个助手项只展示用户可理解的信息：

- 图标与名称
- 一句话描述
- 能力标签（用「文本」「文件」「需要确认」等用户语言，不用 HITL/Published）
- 最近更新时间
- 开始对话按钮

不展示 Workflow、版本号、Published 状态、HITL 标识等内部术语。

## 4. 交互细节

### 会话与助手

- 一个会话固定一个助手；会话中不能切换助手。
- 新对话先选助手再输入；没有合适助手时选择「使用通用对话」（由平台模型 BFF 提供）。
- 已有消息的对话中点「新建对话」→ 返回初始化界面，原会话保留；不在当前会话里切换助手。
- 当前助手始终在对话头部可见。

### 发送

1. 用户发送后立即落一条用户消息。
2. 创建助手占位消息，状态为「正在处理」。
3. 完成后填充结果；失败时保留失败上下文，不伪装成普通回复，并给出「重试 / 修改任务 / 换助手」下一步。
4. 处理信息（耗时、节点摘要）在抽屉中按需查看，不占主区。

### 需要确认（waiting）

审批/补充信息卡片**直接出现在聊天流中**，紧邻对应助手消息：

- 说明为什么需要用户操作
- 将要执行什么
- 可选答案/字段
- 批准、拒绝、提交按钮
- 危险动作使用破坏性操作色；普通补充信息使用主色
- 移动端必须可填写和提交
- 防重复提交，提交后有明确反馈

### 结果

结果支持 Markdown、表格、代码块、结构化 JSON 和下载链接；支持复制、继续追问、重试。执行详情默认折叠在抽屉中，用户主动展开。

### 附件预览

附件预览统一使用 `AttachmentPreviewModal` 组件：

- **图片**：应用内预览，支持多图左右切换（ArrowLeft / ArrowRight）
- **PDF**：应用内 iframe 预览，支持「新窗口打开」
- **Office 文档**（Word/Excel）：降级面板，显示文件类型徽章、文件名和「打开/下载」按钮，不空白 iframe
- **其他格式**：降级面板，明确提示「此格式暂不支持应用内预览」
- **文档摘要**：若助手消息有 `documentSummaries` 且同消息有同名附件，点击摘要可打开对应附件预览
- **交互**：点击遮罩关闭、Esc 关闭、焦点陷阱、`prefers-reduced-motion: reduce` 支持
- **可访问性**：`role="dialog"`、`aria-modal="true"`、标题用文件名、关闭按钮有 `aria-label`

## 5. 状态文案与动作（TASKS P-03 冻结）

| 用户状态 | 文案 | UI 表现 | 用户动作 |
|---|---|---|---|
| idle | 空 | 空状态 + 助手说明 + 示例任务 | 开始输入 |
| 正在处理 | 正在处理… | 助手占位消息 + 轻量指示 | 可取消 |
| 需要确认 | 等待你的确认 | 聊天流内审批/补充信息卡 | 批准、拒绝、填写 |
| 已完成 | 已完成 | 最终结果 + 复制/下载/继续 | 复制、下载、继续追问 |
| 失败 | 处理失败 | 失败原因 + 下一步 | 重试、修改任务、换助手 |
| 已取消 | 已取消 | 已取消状态 | 重新发送 |

> Runtime 状态只在后端 adapter 层映射为上述用户状态；前端不直接展示 RUNNING/WAITING_INPUT 等内部枚举。

## 6. 可访问性与响应式

- 所有图标按钮提供 tooltip 和 aria-label。
- 键盘可完成助手选择、发送和审批。
- 颜色不作为唯一状态信息，状态同时有文字和图标。
- 断点：`>= 1200px` 双区 + 抽屉，`768-1199px` 主区 + 抽屉（会话导航变抽屉），`< 768px` 单栏 + 抽屉。
- 文本不依赖视口缩放，长助手名称和按钮允许换行。

## 7. 设计验收

- 首屏无需滚动即可看到当前助手、对话空状态和输入框。
- 正在处理 / 需要确认 / 已完成 / 失败 / 已取消 可一眼区分。
- 任意消息都能在抽屉中追溯到对应处理记录。
- 审批不中断：需要确认的卡片在聊天流内可直接完成，桌面和移动端一致。
- 刷新和窄屏下布局不发生内容遮挡。
